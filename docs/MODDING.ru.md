# Моды и своё содержимое

**[English version — MODDING.md](MODDING.md)**

Ничто в этой программе не прибито гвоздями к ванильной Victoria 3. Если ваш мод
добавляет ресурс, завод или целую отрасль — опишите это здесь, и калькулятор
будет обращаться с ними точно так же, как со штатным содержимым: тот же
решатель, та же схема, тот же порядок строительства, те же предупреждения.

Путей два. **Пользуйтесь первым.**

---

## 1. Вкладка «Данные» (рекомендуется)

Всё, что вы здесь делаете, хранится отдельно от поставляемых файлов, помечается
значком по всей программе (`+` — вы создали, `✎` — вы изменили), откатывается
по одной записи и выгружается одним файлом, который можно кому угодно
отправить.

### Добавить товар

**Данные → Товары → Новое**

- `id` — маленькими буквами, уникальный, например `mithril`
- Название, категория, базовая цена
- Иконка — выберите одну из 400+ игровых или **Своя картинка** и перетащите
  PNG (меньше 512 КБ; она хранится внутри вашего набора, поэтому копировать
  файлы картинок не нужно)

### Добавить здание

**Данные → Здания → Новое**

- Группа, стоимость постройки
- **Может производить** — все товары, которые оно способно выпускать. Именно по
  этому списку программа ищет ответ на «кто умеет делать мифрил?»
- **Строки методов** — какие строки-переключатели здание предлагает. Возьмите
  готовую (например `pmg_ownership_industry`) или сначала создайте свою.

### Добавить метод производства

**Данные → Группы методов → Новое** для строки, затем **Данные → Методы
производства → Новое** для каждого варианта в ней.

- **Потребляет / уровень** и **Производит / уровень** — те числа, что
  показывает игровая панель здания
- **Рабочие места / уровень** — по профессиям
- Требуемая технология, загрязнение, дополнительная инфраструктура

Порядок важен: программа считает, что следующие методы в строке строго лучше, —
на этом основана кнопка «взять лучший доступный метод». У строки с `rowKind`
= `secondary` вариант «без X» должен идти первым.

### Исправить число, в котором мы ошиблись

Любую поставляемую запись можно изменить так же. Сохраняются только изменённые
поля, поэтому будущее обновление `app/data/` всё ещё достаёт до того, к чему вы
не притрагивались, а **Вернуть** восстанавливает оригинал.

Если вы сверили число с игрой — поставьте ему confidence `verified`: это уберёт
значок `?` со всего, что посчитано с его участием.

### Поделиться

**Данные → Выгрузить в файл** создаёт `что-нибудь.v3pack.json` с вашими
записями, вашими сохранёнными цепочками и, по желанию, настройками. Тот, кому
вы его отправите, откроет **Данные → Загрузить чужой файл** и увидит ровно то
же, что вы.

Загрузка в режиме *добавить* сохраняет его собственную работу; *заменить*
сначала стирает. Цепочка с уже занятым id переименовывается, а не затирает
чужую.

### Проверить себя

**Настройки → Проверить данные на ошибки** проверяет весь комплект: ссылки на
несуществующее, группы методов без методов, товары, которые никто не может
произвести. Именно так обычно ломаются данные модов, и находится это одним
щелчком.

## 2. Правка поставляемых файлов

Так стоит делать, только если вы хотите изменить то, что получают *все*:
исправить ванильную таблицу или сделать форк программы под конкретный
тотальный мод.

1. Правьте нужный файл в `app/data/`. Формат описан в
   [DATA-FORMAT.ru.md](DATA-FORMAT.ru.md), а шапка каждого файла объясняет его
   собственные соглашения.
2. Если добавляете новый файл — добавьте одну строку `<script>` в
   `app/index.html` и одну запись в список `FILES` в `tools/selftest.js`.
3. Если добавляете иконки в `img/icons/` — пересоберите список:
   ```bash
   tools/gen-icon-manifest.sh
   ```
4. Добавьте названия новых записей в `app/lang/ru.js` (и в другие языки):
   английский подставит поле `name`, остальные языки — нет.
5. **Запустите тесты:**
   ```bash
   node tools/selftest.js
   ```

Самопроверка — не украшение. Она ловит висячие ссылки, товары, которых никто не
производит, опустевшие группы методов, недостающие переводы, цепочки, которые
перестали сходиться, и порядок строительства, который вывернулся наизнанку.
Каждое из этого реально случалось при разработке.

## Что стоит знать до начала

**Здание с несколькими необязательными продуктами.** Дайте ему несколько строк
`secondary`, по одной на продукт, с вариантом «без X» первым. НЕ складывайте их
в одну строку `base`: программа включает ровно те побочные строки, которые
нужны цепочке, и именно это не даёт двигателю нести стоимость автомобиля, танка
и самолёта одновременно.

**Метод, общий для нескольких зданий.** Используйте `__primary` как id товара в
`out`. Он раскрывается в первый элемент `produces` здания — так один набор
методов обслуживает кофе, чай, сахар и хлопок.

**Отношения важнее величин.** Сколько нужно зданий, решает *отношение* входа к
выходу. Если правите одно — правьте отношения.

**Следите за разгоном.** Если цепочка потребляет чего-то больше, чем может
произвести, решатель скажет об этом и назовёт здание, вокруг которого рост шёл
быстрее всего. Это проблема данных, а не ошибка программы — проверьте отношение
у этого здания.
