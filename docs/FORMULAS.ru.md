## Одно здание

```
на уровень   = Σ (по одному выбранному методу из каждой строки)
выработка    = 1 + экономия масштаба + бонусы
               экономия масштаба = min(уровни, предел) × 1%     предел = 25

товары вход  = вход на уровень  × уровни × выработка
товары выход = выход на уровень × уровни × выработка
рабочие      = места на уровень × уровни              ← без выработки
```

Отсюда три правила, и они объясняют почти все неожиданности:

1. **Методы складываются.** По одной строке из каждой группы; итог — сумма. У
   строк автоматизации занятость отрицательная намеренно и обрезается нулём.
2. **Выработка масштабирует товары, но не рабочие места.** Завод 20-го уровня
   превращает тот же состав рабочих в на 20% больше товара. Поэтому выгоднее
   складывать уровни в одном штате, чем размазывать.
3. **Занятость — это потолок, а не обещание.** Если в штате нет машинистов,
   здание работает не на полную. Программа предупредит, а не сделает вид.

## Целая цепочка

Вы просите 200 стали. Стали нужны железо и уголь. Железным рудникам нужны
инструменты. Мастерским инструментов нужна сталь. То есть ответ на «сколько
нужно стали» зависит от ответа на «сколько нужно стали». Обход дерева сверху
вниз зациклится навсегда.

Признаём, что это межотраслевой баланс, и решаем как экономисты:

```
x = конечный спрос + A · x
```

`x` — сколько чего надо произвести; `A` — сколько одного товара съедает единица
другого. Начинаем с нуля и применяем уравнение снова и снова. Каждый проход
добавляет следующее кольцо спроса сверху, добавки всё меньше, и через несколько
десятков проходов числа перестают меняться. Эта неподвижная точка **и есть**
ответ, а циклы не требуют особого случая.

```
уровни(здание) = максимум по товарам, за которые оно отвечает, от
                   (спрос − закупка) ÷ (выход на уровень × выработка)
```

Если числа *не* перестают меняться, цепочка потребляет чего-то больше, чем
может произвести. Решатель останавливается после 200 проходов и называет
здание, вокруг которого шёл разгон, а не выдаёт бессмыслицу.

`app/engine/solver.js`

**Баланс товаров**

```
баланс = произведено + закуплено − потреблено − конечный спрос
```

О нехватке сообщается, только если она превышает `max(0.05, поток × 0.0001)`:
итерация оставляет остаток в несколько миллионных, и надпись «нехватка: 0»
приучает людей не читать полосу предупреждений.

## Деньги

```
выручка     = Σ (выход × цена)
затраты     = Σ (вход  × цена)
зарплаты    = Σ (рабочие × вес зарплаты) × базовая ставка × множитель
прибыль     = выручка − затраты − зарплаты
```

Две честные оговорки:

- По умолчанию берутся **базовые** цены. Ваш рынок двигает их на ±75%, и
  цепочка, прибыльная по базовой цене, может стать убыточной, когда вы завалите
  собственный рынок своим же товаром. Товары → Цены → впишите то, что реально
  показывает ваш рынок.
- `baseWagePerWorker` (по умолчанию 0.08) — это **ручка настройки, а не игровая
  константа**. Подгоните её в настройках под здание из своего сохранения, и все
  остальные денежные числа программы сразу станут достоверными.

## Порядок строительства

Обычная топологическая сортировка здесь неприменима: настоящая цепочка — это
один большой цикл, «первого» здания не существует, и наивные алгоритмы выдают
произвольный порядок. Ранняя версия этого файла уверенно советовала строить
текстильную фабрику раньше хлопка.

Правильный инструмент — **конденсация**. Алгоритм Тарьяна находит компоненты
сильной связности — ровно те наборы зданий, которые зависят друг от друга по
кругу, — и после схлопывания каждой в одну вершину остаётся граф, гарантированно
ациклический, который *можно* упорядочить. Тарьян выдаёт компоненты именно в
нужном порядке: компонента только после всего, от чего она зависит.

Внутри цикла кто-то должен пойти первым и какое-то время простоять. Программа
выбирает того, кто меньше всех зависит от собственного цикла, и помечает
«разорванным циклом» только его — честно и по делу, вместо того чтобы разводить
руками на каждом здании списка.

## Время строительства

```
стоимость = Σ (уровни × стоимость здания) × (1 + модификатор стоимости построек)
```

Наивный ответ — `стоимость ÷ очки в неделю`. Он неверен всегда, когда в плане
есть строительные секторы: каждый достроенный приближает все оставшиеся здания,
кривая гнётся. Построить сначала десять стройсекторов, а потом промышленность,
обычно БЫСТРЕЕ, чем строить промышленность сразу, хотя работы больше — и
никаким делением этого не увидеть.

Поэтому очередь моделируется:

```
каждую неделю:
    доступно = недельные очки строительства
    идём по очереди сверху вниз:
        каждой площадке до maxWeeklyPerBuilding, пока очки не кончатся
    любой уровень стройсектора, достроенный на этой неделе,
        со следующей недели повышает недельные очки
```

Рядом показывается плоская оценка — видно, что даёт разгон. Моделирование можно
выключить.

### Сколько стройсекторов стоит строить?

Оптимум существует, но замкнутой формулы для него нет. Каждый уровень сектора
приближает всё, что идёт после него, но его самого надо построить, и он тянет за
собой дерево, железо, инструменты и сталь — то есть ещё здания и ещё стройку.
Слишком мало — ползёте; слишком много — последние достроятся уже после того, что
должны были ускорить.

Поэтому программа не гадает. Для каждого варианта количества она пересобирает
весь план — секторы, их поставщиков, всё, — упорядочивает, моделирует очередь и
оставляет то количество, которое финиширует раньше. Перебор останавливается
досрочно, когда время несколько раз подряд ухудшилось: кривая U-образная.
Типичная цепочка просчитывается примерно за 15 мс.

Полезное наблюдение, которое даёт перебор: при низком стартовом строительстве
закладывать много секторов сразу — МЕДЛЕННЕЕ, потому что строить их придётся на
текущей черепашьей скорости, прежде чем хоть один окупится.

## Военное дело

```
товары в неделю = Σ по батальонам (мирный вход × военный множитель при мобилизации)
                + мобилизационные опции, считаются на каждый батальон

атака = Σ (батальоны × атака метода)     — относительная, не предсказание боя
```

Дальше эти товары идут через обычный решатель цепочек, потому что армия — это
просто ещё один заказ вашим заводам. Программа считает мирный и военный счёт
отдельно: разрыв между ними и решает, может ли страна воевать.

## Исследования

```
произведено = Σ (уровни университетов × выход метода)
потолок     = ограничение по грамотности
эффективно  = min(произведено, потолок)
недель на технологию = стоимость ÷ эффективно
```

Исследования — единственная цепочка, где узкое место обычно не здания. Выше
потолка грамотности лишние уровни университетов нанимают учёных и не дают
ничего — программа показывает оба числа рядом, чтобы это было видно сразу.

`app/engine/research.js`
