# Формат данных

**[English version — DATA-FORMAT.md](DATA-FORMAT.md)**

У каждой записи есть три общих поля:

| Поле | Смысл |
|---|---|
| `id` | внутренний ключ и половина ключа перевода (`good.coal`) |
| `name` | английское название по умолчанию; другие языки переопределяют его в `app/lang/` |
| `confidence` | `'verified'` (сверено с вики) или `'approx'` (оценка — программа рисует значок `?`) |

`kind` — **зарезервировано**: реестр записывает туда тип записи и перезапишет
ваше значение. Именно поэтому у группы методов производства собственное поле
называется `rowKind`. Реестр громко предупреждает, если файл данных пытается
задать `kind`.

---

## Товар — `app/data/goods.js`

```js
{ id: 'coal', name: 'Coal', category: 'industrial', basePrice: 30,
  icon: 'Goods_coal', confidence: 'verified', order: 21 }
```

| Поле | Смысл |
|---|---|
| `category` | `staple` \| `industrial` \| `luxury` \| `military` \| `abstract` |
| `basePrice` | £ — базовая цена игры; рынок гуляет вокруг неё ±75% |
| `abstract` | `true` для строительства / бюрократии / инноваций: сделаны товарами, чтобы работал тот же решатель, но на рынке их нет |
| `aka` | прежнее название, например Engines до 1.5 назывался Locomotives |

## Здание — `app/data/buildings.js`

```js
{ id: 'steel_mills', name: 'Steel Mills', group: 'manufacturing',
  constructionCost: 400, produces: ['steel'], unlockTech: 'tech_pig_iron',
  pmGroups: ['pmg_steel_base', 'pmg_automation_heavy', 'pmg_ownership_industry'],
  icon: 'Building_steel_mills', confidence: 'approx', order: 56 }
```

| Поле | Смысл |
|---|---|
| `group` | см. `building_groups.js`; даёт значения по умолчанию для пропущенного |
| `constructionCost` | очки строительства на **один** уровень |
| `produces` | все товары, которые здание *может* выпускать любыми методами — по этому списку ищется «кто умеет делать сталь?» |
| `pmGroups` | строки-переключатели из игровой панели здания, по порядку |
| `infraUsage` / `providesInfra` | на уровень; пропустите `infraUsage`, чтобы взять из группы |
| `abstractOutput` | `'construction'` \| `'bureaucracy'` \| `'innovation'` |
| `militaryKind` | `'army'` \| `'navy'`; вместе с `battalionsPerLevel` |
| `maxPerState`, `autoBuilt` | одно на штат; строится игрой, а не вами |

Само по себе здание не производит ничего. Что оно производит, решают включённые
методы производства.

## Группа методов — `app/data/pm_groups.js`

Одна строка в игровой панели здания. В каждой строке выбирается ровно один
метод, а итог здания — **сумма** по строкам.

```js
{ id: 'pmg_steel_base', name: 'Base Production', rowKind: 'base', order: 1 }
```

`rowKind` важнее, чем кажется:

| `rowKind` | Что выбирается по умолчанию |
|---|---|
| `base` | самый продвинутый из открытых |
| `automation` | самый продвинутый из открытых |
| `ownership` | самый продвинутый из открытых |
| `secondary` | **выключено**, пока цепочке реально не нужен этот продукт |
| `mobilization` | выключено; включается по армиям на военном экране |

Правило про `secondary` — несущее. Если включить все необязательные строки по
умолчанию, каждый двигатель начинает нести стоимость входов автомобиля, танка
*и* самолёта одновременно, и цепочка раздувается до математической
нерешаемости.

## Метод производства — `app/data/pm_*.js`

Пишется через помощник `V3.pmList`, чтобы таблица читалась как игровая панель:

```js
V3.pmList('pmg_steel_base', [
  ['pm_bessemer_process', 'Bessemer Process', {
    icon: 'Method_bessemer_process', tech: 'tech_steel',
    in:   { iron: 45, coal: 30 },
    out:  { steel: 45 },
    jobs: { laborers: 4000, machinists: 1000 },
    pollution: 16
  }],
  ...
]);
```

| Ключ | Смысл |
|---|---|
| `in` / `out` | товары на уровень в неделю — ровно те числа, что показывает игровая панель |
| `jobs` | **изменение** занятости на уровень; у строк автоматизации оно отрицательное намеренно |
| `tech` | id нужной технологии либо пропуск |
| `pollution`, `infra` | на уровень |
| `unit` | только для военных: `{ offense, defense, kind }` |
| `warMult` | только для военных: множитель к `in` при мобилизации |
| `note` | свободный текст, показывается при выборе метода |

**Порядок в массиве — это порядок улучшения.** Программа считает, что каждый
следующий метод строго лучше; на этом основана кнопка «взять лучший доступный
метод».

**`__primary`** в качестве id товара означает «первый элемент `produces` этого
здания». Это позволяет одному набору методов обслуживать все плантации и делает
так, что строка удобрения повышает урожай хлопка на хлопковой плантации, а не
загадочным образом выращивает там пшеницу.

## Профессия — `app/data/pops.js`

```js
{ id: 'machinists', name: 'Machinists', strata: 'poor',
  wageWeight: 2, qualification: 'basic', icon: 'Pop_machinists' }
```

`wageWeight` — доля фонда зарплаты здания на одного попа относительно рабочего.
`qualification` — `none` / `basic` / `educated`, из неё берутся предупреждения
«вам ещё некем это укомплектовать». `owner: true` означает оплату из прибыли.

## Технология — `app/data/technologies.js`

Только ограничитель: `{ id, name, era: 1..5, category }`. Программа не
моделирует дерево технологий; ей нужно ответить лишь «доступен ли мне этот
метод?».

## Статья альманаха — `app/data/almanac.js`

Только структура — каждое предложение лежит в `app/lang/*.js` и вызывается по
ключу, поэтому перевести всё руководство = перевести один файл. Типы блоков:
`p`, `tip`, `warn`, `steps`, `goods`, `formula`, `allFormulas`, `compare`,
`table` и `chain` — **живой** разбор, который прогоняет настоящий решатель.

## Файл набора — `что-нибудь.v3pack.json`

Всё добавленное и изменённое в одном файле, который можно кому угодно отправить.

```json
{
  "format": "vic3calc.pack",
  "formatVersion": 1,
  "appVersion": "1.0.0",
  "gameDataRevision": "2026-09-08",
  "title": "Anbennar goods pack",
  "author": "кто-то",
  "createdAt": "2026-09-08T10:00:00.000Z",

  "data": {
    "good":     { "mithril": { "name": "Мифрил", "category": "industrial",
                               "basePrice": 120, "icon": "Goods_iron" } },
    "building": { "steel_mills": { "constructionCost": 380 } },
    "pm":       { "pm_bessemer_process": { "outputs": { "steel": 50 } } }
  },

  "chains":   [ { "id": "chain_a1b2", "name": "Сталь 200", "targets": [ ... ] } ],
  "settings": { }
}
```

Правила, благодаря которым наборы можно накладывать друг на друга:

- Запись в `data` — это **правка**, а не замена: хранятся только изменённые
  поля, поэтому будущее обновление `app/data/` всё ещё достаёт до полей, к
  которым вы не притрагивались.
- `{ "__deleted": true }` скрывает поставляемую запись.
- Загрузка в режиме *добавить* сохраняет ваше; *заменить* сначала стирает.
- Цепочка с уже занятым id получает новый, а не затирает чужую.
- `icon` может быть ключом из `app/data/icon_manifest.js` либо `data:`-URL —
  своя иконка едет внутри того же файла, копировать картинки не нужно.
- Набор с более новым `formatVersion` отклоняется, а не применяется наполовину.
